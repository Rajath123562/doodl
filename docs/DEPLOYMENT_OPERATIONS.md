## Local setup once Antigravity has written real app source

Run on Windows PowerShell in the generated `app/` directory; adapt if the real `package.json` differs:

```powershell
node --version
npm --version
npm install
npm run dev
npm run lint
npm run typecheck
npm test
npm run test:e2e
npm run build
```

**These commands will not start a multiplayer server from this handoff ZIP alone.** They become valid after the agent creates and documents the actual application. Never run `npm audit fix --force` blindly and break compatibility.

## Cloudflare account steps (human authorization)

1. Make or access your Cloudflare account via its official site, confirm plan and region/account configuration.
2. Review the application's `wrangler.jsonc`, DO namespace bindings, `new_sqlite_classes` migrations and environment settings generated by the agent. Confirm they use the *current documented* config format.
3. Authenticate using official Wrangler login in your terminal:

```powershell
npx wrangler login
```

4. Add application secrets using Cloudflare secret storage (`wrangler secret put ...`, or the current officially documented procedure). **Never paste secret values into chat or commit them.** Do not create insecure `.env` with real production secrets in the repo.
5. Deploy to staging first using the project-provided script (`npm run deploy:staging` if implemented). Confirm resource names/config and costs; no deploy or paid account switch without user approval.
6. Run real two-user/two-network staging E2E tests and a manual mobile test. Only then deploy public release (`npm run deploy` or equivalent after review).
7. Record URL, deployment time, commit SHA, migrations, tested browser versions and rollback revision in `RELEASE_REPORT.md`.

## Free plan economic reality (verified from Cloudflare November 2026 docs; reconfirm before launch)

- Cloudflare Durable Objects are available on Workers Free if using **SQLite-backed DOs**.
- Reported Durable Object Free included limits: **100,000 requests per day**, **13,000 GB-s duration per day**, **5 GB stored data total**, and storage read/write daily limits. When exceeded, Free plan operations can fail instead of silently scaling forever.
- Incoming WebSocket messages contribute toward request usage; drawing events must be batched and measured, not treated as free unlimited traffic.
- Worker-level limits apply separately. Do not assume 100,000 requests can support a specific player count without an event and match-duration traffic model.
- Set budget/spending alerts where available. Do not upgrade to any paid plan without explicit human approval.

## Monitoring (must be implemented, not hypothetical)

- Structured log fields: `timestamp`, `requestId`, `roomHash` (avoid plain room code where possible), `eventType`, `durationMs`, `resultCode`, `stateVersion`. Never log secret word/session credential/raw guesses unnecessarily.
- Error-rate alarms for WebSocket upgrades, unauthorized events, unhandled DO exceptions, stale-room failures, room join rejects, slow response and storage errors.
- Dashboards: daily rooms, active seats, message count per room, incoming event error count, secret leakage guard tests, WebSocket disconnect count, daily DO requests/duration/storage.
- Synthetic E2E for two-user room and key API health check; ensure synthetic accounts don't pollute real leaderboards.

## Failure and rollback

- Turn off public matchmaking if spam/abuse spikes. Preserve private room games when possible.
- If upgrades break room protocol, use version negotiation/compatibility window; old sockets receive upgrade-required rather than silently corrupting state.
- Handle loss of DO storage or inability to deploy with a user-facing maintenance message, not fake success.
- If a migration is destructive, require backup and documented rollback; prefer additive migrations during active games.
- Preserve latest known-good production commit and tested rollback route; perform staged rollout or manual revert after testing.

## Before real public launch

Security review and dependency audit; privacy/safety policy; Terms/community rules; origin/domain and HTTPS checks; GDPR/Indian data handling consideration as applicable; user reporting and moderation response process; server cost model; mobile verification; support contact/bug report channel. No claim of “100% bug-free.”
