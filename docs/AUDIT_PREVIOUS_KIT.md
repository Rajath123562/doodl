# Independent desk review of the previous 40-file kit — V3 corrections

## What was actually inspected

The original `DOODL_Antigravity_Complete_Build_Kit.zip` was opened and enumerated: 40 files including basic MD specifications, nine phase prompts, three contract references, offline V2 HTML and six previews. Its broad architecture and honesty about simulated players were sound. However, a broad plan is not the same as an implementation-complete production spec. The following material gaps existed or were under-specified.

| Gap in V2 handoff | Why it matters | V3 mitigation |
|---|---|---|
| Design described aesthetically, not screen-by-screen/states | Agent can create pretty but unusable views | `02_SCREEN_BY_SCREEN_UI`, `03_DESIGN_TOKENS`, `04_USER_JOURNEYS`, `19_UX_COPY` |
| No hard traceability from every feature to proof | Easy to declare complete with omissions | `20_DEFINITION_OF_DONE_AND_TRACEABILITY`, `FEATURE_ACCEPTANCE` |
| Session takeover and multi-tab complexity too abstract | Guest spoofing/score duplication | `05_ROOM_AND_IDENTITY_LIFECYCLE`, `09_AUTH_THREAT_MODEL_ABUSE` |

## What V3 can and cannot guarantee

V3 makes **project expectations more explicit and auditable**. It does **not** turn a handoff ZIP into a complete game or guarantee zero missing defects: successful implementation and production QA require running actual code, load simulation, user testing, staging deployment, operational monitoring and security review. Code generated by an agent can still contain logic mistakes, cost issues and vulnerabilities.

## Decision precedence

1. Secure authoritative identity/state and player safety.
2. Deterministic gameplay correctness and data privacy.
3. Concrete acceptance requirements from `20_DEFINITION_OF_DONE_AND_TRACEABILITY.md`.
4. Existing foundational technical design in `GAME_ENGINE`, `REALTIME_PROTOCOL`, `DRAWING_ENGINE`.
5. Detailed UX/feature specs, subject to executable constraints.
6. Reference demo appearance; cannot override accessibility or correctness.

If there is a conflict, write an ADR and repair the conflict in source/spec; **never silently pick one of two inconsistent requirements**.

## Concrete wire-contract corrections discovered during this review

The V2 handoff's `client-event-envelope.schema.json` expected fields `id`, `roomCode`, `data`, while V2 protocol prose and the sample envelope in this kit expected `clientEventId`, `payload`, with match/turn IDs. Those cannot be treated as one protocol. V3 changes the JSON Schema, TypeScript references and sample events to a **single** canonical envelope and requires runtime per-type validators. Similarly V2's room settings schema allowed only `[30,60,90,120]` and `cycles`, while its gameplay docs described Blitz as 20–45 seconds and `cyclesPerPlayer`; V3 uses conditional mode-specific draw times and uniform `cyclesPerPlayer`. Antigravity must implement/tests against V3 schema and search for any stale field vocabulary in source before shipping.
